从零读懂HCCL新Selector

从一次AllReduce走进代码 · 完整17节原文整理

先看交互图解 ←

这篇文章面向第一次接触HCCL算法选择代码的读者。你不需要先掌握集合通信算法，也不需要一上来就看懂所有C++模板。我们先解释它解决什么问题，再沿着真实调用链逐步展开。

本文中的“新Selector”特指SelectorEngine、CostModel、CostTable、AlgAttrs组成的选择流程。源码来自HCCL仓库，核对版本为170ddeec539b4d693028ce6e0cf5c58933e4d46d，编写日期为2026-09-12。下面的默认值、支持范围和实现细节都针对这个本地版本。

先记住一句话：新Selector拿到本次通信的需求和机器连接情况，从可用算法中选出最终代价最小的一个，并把算法名和执行配置交给后续执行流程。

网页中的源码引用显示为仓库相对路径，可在对应版本的本地HCCL仓库中搜索定位。代码摘录可能省略日志等内容；标注“伪代码”的片段只用于解释，不能直接替换源码。数值算例会明确说明哪些来自代码，哪些是假设。

1. Selector为什么存在

假设4张卡一起训练模型，每张卡算出了一份梯度。它们需要把梯度加起来，再让每张卡都得到相同的结果。

如果每张卡只有一个数字：

开始：rank0=1，rank1=2，rank2=3，rank3=4
执行AllReduce，归约操作为SUM
结束：rank0=10，rank1=10，rank2=10，rank3=10

“把所有人的数据合起来，再让所有人拿到结果”规定了要完成的任务。但它没有规定每张卡要先联系谁、发多少数据、分几轮通信、由哪个执行引擎下发任务。

实现同一个AllReduce，可以有不同通信算法。它们算出的结果应满足算子语义，但运行时间可能不同。小数据量时，启动和同步开销比较显眼；大数据量时，传输效率更关键。卡数、卡之间的连接方式、支持的数据类型也会限制算法是否可用。

因此，HCCL需要先做一个选择：这次调用，在当前环境里，应该使用哪个算法实现？

可以把Selector想成运输方案选择员：

通信里的对象 运输类比
本次算子参数 货物、重量、起点终点和运输要求
拓扑 道路连接情况
算法属性 每种运输方案能走哪些路、能运哪些货
代价模型 各方案的估时方法
代价表 针对这批货算出的预计耗时列表
执行器和模板 按选定方案组织并完成运输

这个类比只帮助理解职责。实际Selector在本地CPU代码中分析参数和模型；真正的数据传输由后续执行器、模板和HCOMM接口完成。

2. 先认识几个基础概念

2.1 算子、算法、执行器、模板、引擎

这五个词不能混用。

名称 回答的问题 本文真实例子
算子（op） 要完成什么通信任务？ HCCL_CMD_ALLREDUCE
算法（algorithm） 选定哪一个具体实现方案？ AicpuAllReduceSoleMeshOneShot
执行器（executor） 如何组织整个算法的资源和执行过程？ InsV2AllReduceSoleExecutor
算法模板（template） 具体通信步骤怎样实现？ InsTempAllReduceMesh1DOneShot
执行引擎（engine） 通信任务由哪种机制执行或调度？ AICPU_TS

执行器可以组合一个或多个算法模板。一个执行器类也可以通过不同C++模板参数，形成不同的算法实现。

注意这里有两种“模板”：“算法模板”是通信实现组件；C++的template <typename ...>是把类型当作参数的编程语法。项目用后者组合前者，两者相关但不是同一个概念。

2.2 Rank和通信域

rank可以先理解成一次通信中的成员编号。4个参与者通常编号为0、1、2、3。

userRank表示本成员的编号，userRankSize表示通信域里一共有多少成员。

HcclComm comm是通信域句柄。句柄类似一个“凭证”：把它交给接口，就可以查询对应通信域的状态、拓扑和上下文，不需要直接访问内部结构。

2.3 拓扑

拓扑描述参与者之间怎样连接。不同连接方式支持的算法和性能不同。入门时先抓住下面几项：

字段或术语 阅读时怎么理解
topoLevelNums 当前拓扑包含多少层级
level0Topo 第0层的形状分类
MESH_1D 一种Mesh形状分类
CLOS 一种交换网络形状分类
MESH_1D_CLOS Mesh与CLOS相关的混合形状分类
level0PcieMix 第0层是否存在代码所识别的PCIe混合场景
netLayerDetails 更细的网络层、实例、连接等信息

先把TopoInfoWithNetLayerDetails当成“当前机器连接情况的说明书”。不要仅凭某个字段名就把某一层固定等同于一台服务器：具体物理层和算法层的映射，要看拓扑生成和MatchTopo代码。

2.4 数据个数不等于字节数

假设DataDes.count = 262144，类型是FP32，每个元素占4字节：

元素个数 = 262144
字节数   = 262144 × 4 = 1048576B = 1MiB

普通AllReduce的代价表数据量就是这样计算的。后面有多个名为count的字段，只有其中一部分表示元素个数。

2.5 HCCL与HCOMM的边界

本仓负责集合通信算子、算法选择和算法组织。拓扑查询、通信资源及基础通信能力通过HCOMM接口提供；跨仓接口使用本仓src/common/hcomm_dlsym/中的动态符号适配。

阅读Selector时，遇到HcclEngineCtxGet这类调用，可以先理解为“通过接口取通信域上下文”，无需跳进HCOMM内部实现。架构依据见架构简介
docs/zh/architecture/architecture-brief.md。

3. 新旧Selector的区别

仓库里仍然同时存在两套流程。

旧流程的入口是ExecuteSelector::Run
src/ops/op_common/selector/execute_selector.cc。普通分支从SelectorRegistry取得该算子的选择器列表，按照std::map中的优先级键顺序遍历；某个选择器返回MATCH，就结束选择。isMc2还有单独处理分支。

新流程的入口是SelectorEngine::Run
src/ops/op_common/selector/selector_engine.cc。它先形成候选算法及模型，再为本次调用生成代价表，可选地交给Tuner调整，最后比较代价。

对比点 旧流程 新流程
主要入口 ExecuteSelector::Run SelectorEngine::Run
组织方式 按顺序询问选择器是否匹配 过滤候选，计算并比较代价
主要注册信息 SelectorRegistry中的选择器 算法目录、执行器工厂、算法属性
每次决策的主线 找到返回MATCH的选择器 找到有效候选中代价最小的算法
调优介入点 由具体旧选择逻辑决定 Tuner可以修改当前代价表

新流程也有硬规则，例如拓扑条件、数据类型条件和优先保留回调。它不是让所有算法无条件参加比赛。

另外，“旧Selector分支”和API入口的“HCOMM历史兼容路径”是两个不同层次的分流。第5节会分别说明。

4.2 看懂主流程需要的C++语法

以下是实际函数签名：

HcclResult SelectorEngine::Run(
    HcclComm comm,
    OpParam& param,
    TopoInfoWithNetLayerDetails* topoInfo,
    std::string& algName)

逐项翻译：

写法 含义
HcclResult 返回状态码；成功通常是HCCL_SUCCESS
SelectorEngine::Run SelectorEngine类里的Run函数
OpParam& param 引用调用方的参数对象，函数里修改它会影响调用方
TopoInfoWithNetLayerDetails* topoInfo 指向拓扑对象的指针，使用->访问成员
std::string& algName 算法名输出位置，函数会把选中的名字写进去

常见语法还包括：

写法 阅读方法
param.opType 取对象的成员
topoInfo->userRankSize 取指针指向对象的成员
const T& x 通过这个引用读取对象，不修改它
auto x = ... 让编译器推断类型
std::vector<T> 可以增长的数组
std::map<K,V> 根据键查值，按键排序
std::set<T> 保存不重复的值，用于检查是否属于某个集合
nullptr 空指针
return {} 返回空对象；在返回vector的函数中通常表示空数组
Global()、Instance() 本项目中常用于取得一个共享管理对象
std::unique_ptr<T> 管理一个对象的所有权，离开作用域时自动释放
std::call_once(flag, fn) 同一个标志下只执行一次初始化函数

遇到CHK_RET(Foo())，可以先按下面的解释性伪代码阅读：

HcclResult ret = Foo();
if (ret != HCCL_SUCCESS) {
    return ret;
}

因此，CHK_RET(SelectorEngine::Global()->Run(...))返回错误时，外层函数会直接返回错误，不会自动接着运行else里的旧选择器。

5. 一次调用怎么进入新Selector

5.1 总调用链

以进入本仓普通选择路径的AllReduce为例：

HcclAllReduce
  └─ AllReduceOutPlace
      └─ AllReduceOutPlaceCommon
          ├─ FillAllReduceOpParam：整理算子参数
          ├─ HcclGetOpExpansionMode：确定初始执行配置
          ├─ Selector
          │   ├─ HcclCalcTopoInfo：取得拓扑信息
          │   └─ SelectorEngine::Run：新Selector
          └─ HcclExecOp：根据选定算法进入执行流程

对应all_reduce.cc
src/ops/all_reduce/all_reduce.cc和op_common.cc
src/ops/op_common/op_common.cc。

这是一条有条件的路径。API入口的版本/设备兼容判断、零数据返回，以及公共流程中的单rank处理、CCU快速启动、AIV缓存重放等，都可能提前结束或转入其他路径。因此，设置新Selector开关，不等于每次API调用都会运行SelectorEngine::Run。

5.2 新旧流程切换条件

Selector()中的核心分支如下，省略了旧分支构造对象的具体写法：

if (IsNewSelectorEnabled() && SelectorEngine::IsOpSupported(param.opType)) {
    CHK_RET(SelectorEngine::Global()->Run(comm, param, topoInfo.get(), algName));
} else {
    // 创建ExecuteSelector，再调用其Run。
}

需要同时满足两个条件：开关开启，算子在新Selector白名单里。

开关由alg_env_config.cc
src/common/alg_env_config.cc中的ParseNewSelector()解析：

export HCCL_USE_NEW_SELECTOR=1

把它设置在启动通信程序之前。当前代码默认关闭；0表示关闭，1表示开启，其他非空非法值会返回HCCL_E_PARA。不能因为错误日志里有“default to [0]”，就认为非法值会被静默接受。

当前IsOpSupported()实际包含15种：AllReduce、ReduceScatter、AllGather、Reduce、Scatter、Broadcast、Barrier、BatchSendRecv、AlltoAllV、AlltoAllVC、AllGatherV、ReduceScatterV、Send、Receive、AlltoAll。

白名单表示可以进入新流程；它不保证任意拓扑、类型和执行配置下都有算法可选。

若构建启用了HCCL_ALGO_PLUGIN_ENABLE，Selector()在上述分支之前还有算法插件快速路径。该插件成功处理时，可以提前返回。这与稍后修改代价表的Tuner是不同机制。

6. 四份核心数据分别是什么

6.1 OpParam：这次要做什么

OpParam字段很多，先关注这些：

字段 用途
opType 算子类型
DataDes.count 普通算子的数据元素个数
DataDes.dataType 普通算子的数据类型
reduceType SUM、PROD等归约操作
inputPtr/outputPtr 输入和输出内存地址
inputSize/outputSize 输入和输出内存大小
opExecuteConfig 进入选择时的执行配置；选中后会被更新
engine 后续使用的通信引擎，由外层根据配置设置
opMode/isCapture 单算子/图等执行场景信息
commOpExpansionMode 通信域算子展开模式，例如AIV_ONLY约束来源

AlltoAll系列和V类算子使用各自的数据描述字段，不能一概读取DataDes。

6.2 AllAlgos：有哪些已登记的算法

在cost_model.h中，AllAlgos保存AlgElement数组。一个条目包含：

algName       算法名
executorName  执行器名称
templateName  模板名称数组
templateNum   模板数量
opType        算子类型

它像算法目录。登记在目录里，不代表已经适合当前机器，也不代表可以生成有效代价。

6.3 AlgAttrs：每个算法有什么能力限制

AlgAttrs分成两部分：

AlgAttrs
  ├─ name / opType / engine / algoTypes：算法身份
  ├─ topo：拓扑侧属性
  └─ op：本次算子调用侧属性

topo用于模型构建阶段，描述层数、拓扑形状、设备、rank数量等要求。

op用于生成本次代价表，描述数据类型、PROD归约、输入输出重叠、浮点保序等要求。

这样可以把“算法适用条件”放在算法注册附近，而由公共代码统一检查。

6.4 CostModel与CostTable：估时方法和本次报价

这是最重要的一组区别。

CostModel
  └─ costAlgoParams[]
      ├─ algName
      ├─ param[]：一组或多组(A,B,C,D)
      └─ count：这个算法有多少组系数

CostTable
  └─ costs[]
      ├─ algName
      └─ cost：针对当前数据量算出的一个数值

CostModel回答“这个算法如何估算代价”；CostTable回答“这次调用中，这个算法的代价是多少”。

字段 count在这里的真实含义
OpParam.DataDes.count 数据元素个数
AllAlgos.count 目录中的算法条目数
CostModel.count 模型中的算法条目数
CostAlgoParams.count 单个算法的系数组数；小于等于0时不进入代价表
CostTable.count 当前代价表中的算法条目数

所以cm.costAlgoParams[i].count = 0表示禁用这一算法的模型条目。它不是把本次通信的数据量改成0，也不一定缩短外层模型数组。

7. 算法怎么注册进来

7.1 三个地方分别保存什么

组件 保存内容 后续用途
AllAlgos 算法名、算子、执行器名、模板名 枚举所有已登记算法
CollAlgExecRegistryV2 (算子类型, 算法名) → 创建执行器的函数 建模或执行时创建对象
AlgAttrsRegistry 算法名 → AlgAttrs 查询适用条件和身份信息

执行器注册宏会同时登记工厂函数和算法目录；属性由另一条宏登记。

7.2 一条真实注册语句

来自ins_v2_all_reduce_sole_executor.cc：

REGISTER_EXEC_V2(
    HcclCMDType::HCCL_CMD_ALLREDUCE,
    AicpuAllReduceSoleMeshOneShot,
    InsV2AllReduceSoleExecutor,
    TopoMatchOneLevel,
    InsTempAllReduceMesh1DOneShot);

用自然语言读：

“登记一个AllReduce算法，名字叫AicpuAllReduceSoleMeshOneShot。需要它时，创建一个组合了TopoMatchOneLevel和InsTempAllReduceMesh1DOneShot的InsV2AllReduceSoleExecutor。”

组合后的C++类型可以写成：

InsV2AllReduceSoleExecutor<
    TopoMatchOneLevel,
    InsTempAllReduceMesh1DOneShot>

注册宏内部用#name把宏参数变成字符串，用DefaultExecCreatorV2<...>登记对象创建函数，再调用AddAlgToAllAlgos(...)加入算法目录。

你没有在Run()里看到显式执行这些注册语句，是因为宏定义了文件级静态变量，初始化这些变量时会调用注册函数。前提是对应代码被构建并加载进程序。

7.3 属性注册宏

REGISTER_ALG_ATTRS(...)内部大致做下面几件事：

  1. 创建一个带默认值的AlgAttrs a。
  2. 让topo和op分别引用a.topo、a.op。
  3. 调用ParseAlgName，从算法名解析身份信息。
  4. 执行宏参数里给出的属性赋值和回调设置。
  5. 把完整属性登记到AlgAttrsRegistry。

例如下面这种写法中的topo不是神秘的全局变量，而是宏内部提供的引用：

// 解释性示意，真实算法的完整属性见第11节。
REGISTER_ALG_ATTRS(
    SomeAlgorithm,
    topo.maxTopoLevelNum = 1;
    op.isSupportProd = false;
);

宏里常见的[] { ... }()是“定义一个匿名函数并立即调用”。若把匿名函数存到topoCustomCheck中而没有末尾调用括号，它就是留待以后执行的检查函数。

7.4 算法名字也参与程序逻辑

把AicpuAllReduceSoleMeshOneShot拆开：

Aicpu | AllReduce | Sole | MeshOneShot
引擎     算子        执行组织  模板方案标识

ParseAlgName、GetEngineByAlgName和AlgoNameMapper都使用名称规则。改名会影响引擎识别、属性解析、算法配置匹配和Tuner维度映射。

当前引擎前缀映射为：

算法名前缀 OpExecuteConfig
Aicpu AICPU_TS
Aiv AIV
CcuMS CCU_MS
CcuSched CCU_SCHED
Dpu HOSTCPU

无法识别的前缀在GetEngineByAlgName中默认归到AICPU_TS。这不是名字随便写也能正确工作的保证。

8. CostModel怎么生成和缓存

8.1 先决定允许哪些引擎参加

SelectorEngine::GetEnginePriority()返回下表：

输入执行配置 返回的候选引擎
CCU_MS CCU_MS、CCU_SCHED、AICPU_TS、HOSTCPU
CCU_SCHED CCU_SCHED、AICPU_TS、HOSTCPU
AIV AIV、AICPU_TS、HOSTCPU
AIV_ONLY AIV
AICPU_TS AICPU_TS、HOSTCPU
HOSTCPU HOSTCPU
其他值 AICPU_TS、HOSTCPU

虽然函数名有Priority，FilterCmByEngine()实际把这些引擎放进set，检查每个算法是否属于候选集合。

**这些候选可以一起进入后续代价竞争。**这里没有“只要CCU_MS有算法，就绝不考虑AICPU”的比较逻辑。后续属性、算法配置和优先规则仍然可能进一步缩小候选集合。

AIV_ONLY的不同之处是集合里只有AIV。

8.2 先处理特殊AIV切换

Run()最前面会检查AutoSelectorBase::IsRollBackAiv()。某些受资源限制的PCIe混合场景下，它会把param.opExecuteConfig改成AIV_ONLY。

具体条件在auto_selector_base.cc
src/ops/op_common/selector/auto_selector_base.cc：涉及部分AlltoAll/INT64归约场景，以及部分单服务器P2P连接场景。

这一步发生在获取模型之前。因此，分析一次选择时，不能只看进入Run()前记录的执行配置。

8.3 模型构建主循环

CostModelManager::InitCostModel()可以按下面的伪代码理解：

for (算法目录里的每个算法) {
    if (!拓扑属性匹配) {
        continue;
    }

    executor = 根据算子类型和算法名创建执行器;
    if (executor不存在) {
        continue;
    }

    params = executor->CalcCostCoeff(...);
    if (params为空) {
        continue;
    }

    保存算法名和系数数组;
    登记executor->GetAlgNetMeta(...);
}

应用拓扑优先规则;

这里遍历全局算法目录，使用每个目录条目自己的opType创建执行器。它没有在循环起点只保留“本次调用的算子类型”；本次算子类型的筛选主要在代价表阶段。

CalcCostCoeff()返回空数组表示这次没有可用模型，日志写为uncalibrated。原因既可能是未实现模型，也可能是模板显式限制了rank数量，或更细的拓扑匹配失败。不要把这个日志词只理解成“缺少实测标定数据”。

8.4 拓扑过滤具体检查什么

CheckAlgoMatchTopoWithReason()根据属性检查：层数范围、第0层形状、部分CCU场景的Mesh类型、2Die支持、PCIe混合支持、Level1Nhr、Mesh连通要求、设备类型、HostDpuOnly、rank上限，以及自定义拓扑回调。

不是每个字段在所有场景都无条件检查。例如Mesh子类型检查有引擎和形状条件。学习具体算法时，应从其注册属性跳到该函数，看相应字段被怎样使用。

位掩码判断容易看花眼。下面的表达式意思是“允许两类形状”：

topo.supportLevel0Topos = LEVEL0_TOPO_MESH_1D | LEVEL0_TOPO_MESH_1D_CLOS;

每种形状对应一个二进制位，|把允许的位合起来；检查时用&判断当前形状对应的位是否设置。

8.5 topoPriorityCheck会提前缩小竞争范围

ApplyTopoPriority()按(opType, engine)分组。

如果某个组里至少一个算法的topoPriorityCheck返回true，该组只保留命中的算法。其他算子或其他引擎的组不受这个组的规则影响。

所以拓扑优先规则是“改变候选集合”，不是“给算法的cost减一点分”。

8.6 缓存保存在哪里

SelectorEngine::InitCostModel()通过通信域上下文接口保存模型，标签这样构成：

std::string costModelTag =
    std::string("costmodel") + "_" + ENGINE_STR_MAP.at(param.opExecuteConfig);

可以理解成：**每个通信域按进入选择时的执行配置保存一份模型。**发生引擎配置回退时，会查询不同标签。

这不是“只存该引擎的算法”：某份模型可以包含该配置允许的多个候选引擎。标签里也没有数据量或当前算子类型。

第一次没有缓存时会构建和保存；后续进入Run()命中该标签，直接使用缓存模型，但仍然生成本次调用的代价表。

模型包含指针，不能只复制结构体外壳。代码先存放CostModel头和CostAlgoParams数组，再为每个算法的系数数组做独立复制。否则临时模型释放后，缓存里的指针可能指向已经释放的内存。

Tuner是否完成初始化使用另一个独立标签"tuner_init"，不随每份执行配置模型重复初始化。

8.7 算法配置过滤

保存模型后，代码依次调用：

FilterCmByEngine(*storedCm, candidateEngines);
FilterCmByHcclAlgo(comm, *storedCm, candidatePrefixes);

前者把候选集合之外的算法count置0；后者根据通信域算法配置或HCCL_ALGO进一步处理模型。

这两类过滤属于模型初始化路径。不能假定在进程中途修改环境变量后，已经缓存的模型就会自动重新过滤。

9. CostTable怎么过滤和计算

9.1 为什么每次还要生成表

同一通信域可能先做一个小数据FP32 AllReduce，再做大数据FP16 AllReduce，还可能调用AllGather。

拓扑大体相同，模型可以复用；本次算子、数据量和内存条件发生了变化，候选和代价需要重新计算。

CostTableGen()调用InitAndFilterByAttrs()，依次处理：

  1. 跳过系数组数小于等于0的模型条目。
  2. 查找算法属性；没有属性则跳过。
  3. 检查属性里的opType是否等于本次算子类型。
  4. 检查数据类型、PROD、内存重叠、保序和自定义调用条件。
  5. 计算当前数据量下的cost并写入表。
  6. 应用opPriorityCheck优先保留规则。

9.2 OpAttrs里的过滤规则

属性 什么情况下会被过滤
supportedDataTypes 非空时，当前类型不在白名单里
unsupportedDataTypes 白名单为空时，当前类型在黑名单里
isSupportProd 为false且本次归约操作是PROD
isSupportInplace 为false且输入输出地址区间有重叠
isSupportFloatOrderPreserved 本次要求严格保序，但算法不支持
opCustomCheck 设置了回调，且回调返回false

白名单非空时走白名单分支，不再检查黑名单。

当前IsInputOutputOverlap()实际比较输入输出地址区间是否相交，不只是判断inputPtr == outputPtr。

浮点加法会受到计算顺序影响；某些调用对归约顺序有更严格要求，所以“数学上都在求和”并不意味着所有归约实现都满足该调用约束。

9.3 opPriorityCheck与拓扑优先规则不一样

opPriorityCheck在本次已经通过普通过滤的代价表中检查。

一旦有算法命中，正常分配成功的路径会只保留命中的算法。当前实现没有按引擎分组，因此它可以影响不同候选引擎之间的竞争。

对照记忆：topoPriorityCheck按(算子, 引擎)分组；opPriorityCheck作用于本次代价表。

9.4 代价计算使用哪个数据量

实际代码是CalcCostTableDataSize()：

算子种类 当前实现取值
普通算子，例如AllReduce DataDes.count × 类型字节数
AllGatherV、ReduceScatterV vDataDes.counts中的最大count乘类型字节数
AlltoAll、AlltoAllV、AlltoAllVC sendCounts指向的第一个值乘发送类型字节数
BatchSendRecv 第一条item的count乘类型字节数
Barrier 0

这是该版本的实际取值，不能把AlltoAllV一行改读为“发送数组全部求和”。模型输入数据量、接口参数inputSize和日志数据量也不应未经核对就视为完全相同。

9.5 A、B、C、D分别是什么意思

CostModelParam包含四个浮点数：

系数 阅读时的含义 在计算中的位置
A 跨卡传输随数据量增长的代价系数 A / util × dataSize
B 本地拷贝、归约等随数据量增长的代价系数 B × dataSize
C 模板的固定时延项 直接加入分段代价
D 任务展开/下发模型项 各段累加后，与通信侧聚合值取最大

模型使用字节和秒量纲计算；例如InitBandwidth()把56乘以十亿存为带宽，CalcLatencyParams()中0.000002表示2微秒。源码中的这些常数是该模型的参数，不能当作所有机器的实测规格或性能承诺。

util是UB带宽利用率修正值。从公式看，利用率越低，同样数据的跨卡传输估计越慢。

一个分段的实际公式为：

segCost = (A / util + B) × dataSize + C

如果算法只有一个分段：

cost = max(segCost, D)

如果有多个分段，先按组内规则聚合，再对组求和；所有分段的D累加，最后取：

cost = max(各组代价之和, 所有D之和)

因此不能把当前公式简写成A×size+B+C+D，也不能把D直接加到每个分段中。

9.6 多段模型为什么需要AlgNetMeta

多阶段算法可能在不同网络上传数据，各段传输比例也不同。AlgNetMeta保存与系数段对应的说明：

字段 作用
netTypes 各段使用的网络类型，用于选利用率表
dataRatios 查利用率时使用的数据量比例
rankSizes 部分算法修正单次传输量时使用的rank数
groupSizes 每组包含多少个系数段
intraGroupMode 组内求和还是取最大
interGroupMode 有该字段，但当前CalcAlgCost()组间固定求和

例如groupSizes={2,1}，组内模式为MAX，表示前两段取最大值形成第一组，第三段形成第二组，两个组再相加。

通信侧聚合值 = max(seg0, seg1) + seg2
最终cost     = max(通信侧聚合值, D0 + D1 + D2)

这是一种建模方式，不代表代码测量了真实执行时的重叠时间。

9.7 利用率怎么查

QueryUbUtil()在Mesh/CLOS表中，用lower_bound找第一个上界大于等于传输量的档位；超出全部档位用最后一个。它是分档查表，没有做线性插值。

查表的数据量一般为：

perTransferSize = dataSize × dataRatio

NHR/NHR_MULTILINK还会乘rankSize/2修正比例。AllGather在CLOS网络上小于1MiB的数据按1MiB查表；AIV会对查到的利用率做util / 0.85 × 0.65修正。

注意：比例主要用于确定查表档位，主公式仍乘dataSize。A/B系数本身也可能已经包含数据比例，不能在主公式外再随意乘一次比例。

10. Tuner、最小值选择和返回结果

10.1 Tuner拿到的是已生成的代价表

TunerEnrichCostTable()先生成表。只有表非空且Tuner已加载，才会补充算法维度并调用插件。

AlgoNameMapper把名字拆成适合插件匹配的维度。例如本文算法可得到：

algName      = AicpuAllReduceSoleMeshOneShot
engineName   = aicpu
executorName = sole
templateName = meshoneshot

这里的executorName=sole是插件维度名，与AllAlgos里的完整执行器类名含义不同。

hccl_tuner_plugin.h
src/ops/op_common/selector/inc/hccl_tuner_plugin.h规定插件可以修改cost：负值表示禁用，0表示偏好，正值表示覆盖原代价，不改则沿用模型值。名字等信息是只读的。

插件收到的是过滤后的候选表，没有一个“任意追加算法并跳过能力检查”的正常接口。给某算法设为0通常使它优先于正代价算法，但若多个算法都是0，仍然会出现并列。

加载相关实现见tuner_setup.cc
src/common/tuner/tuner_setup.cc，环境变量名称是HCCL_TUNER_PLUGIN。没有Tuner也能完成模型选择。

10.2 SelectMinCost逐段阅读

以下摘出实际循环的关键判断：

int minIdx = -1;
float minCost = 0.0f;

for (int i = 0; i < ct.count; ++i) {
    const char* name = ct.costs[i].algName;
    float cost = ct.costs[i].cost;

    if (name == nullptr || cost < 0.0f) {
        continue;
    }
    if (minIdx == -1 || cost < minCost) {
        minIdx = i;
        minCost = cost;
        // 实际代码还记录并列算法，用于日志。
    }
}

minIdx=-1表示还没找到有效候选。因此即使minCost初始值是0，第一个正代价候选也能进入：判断条件左边的minIdx == -1为真。

以后只有遇到更小的cost才替换。代价完全相等时保留原索引，并记录并列日志。因此并列时选表中第一个，不能把它理解成指定引擎获胜，或稳定选择某个按名字排序的算法。

最后写出两个结果：

algName = ct.costs[minIdx].algName;
param.opExecuteConfig = GetEngineByAlgName(algName);

例如以CCU_MS配置进入，若最终选中Aicpu前缀算法，执行配置就更新为AICPU_TS。后续Selector()调用SetCommEngine(param)设置实际通信引擎。

10.3 没选到会怎样

代价表为空，或者没有名字非空且cost非负的候选时，返回HCCL_E_NOT_SUPPORT。

Run()在选择后释放本次ct.costs，成功则打印结果；失败时打印错误。若此时是AIV_ONLY，还会调用LogAivOnlyNotMatch()补充拓扑、参数以及AIV算法的拓扑/算子过滤原因。

这份AIV补充日志没有覆盖每一个阶段。例如一个算法通过拓扑和算子检查，仍可能因没有模型系数、算法配置或Tuner而没有成为有效候选。

11. 真实算法逐段带读

现在用AicpuAllReduceSoleMeshOneShot把前面的概念连起来。

11.1 第一步：找到注册和完整属性

打开ins_v2_all_reduce_sole_executor.cc
src/ops/all_reduce/algorithm/executor/ins_v2_all_reduce_sole_executor.cc，搜索算法名。注册信息如下：

算子：HCCL_CMD_ALLREDUCE
算法：AicpuAllReduceSoleMeshOneShot
执行器：InsV2AllReduceSoleExecutor
拓扑匹配器：TopoMatchOneLevel
模板：InsTempAllReduceMesh1DOneShot

紧接着的属性注册，整理排版后如下：

REGISTER_ALG_ATTRS(
    AicpuAllReduceSoleMeshOneShot,
    topo.maxTopoLevelNum = 1;
    topo.supportLevel0Topos =
        LEVEL0_TOPO_MESH_1D | LEVEL0_TOPO_MESH_1D_CLOS;
    topo.isSupportLevel0PcieMix = true;
    topo.requireAllMeshConnected = true;
    topo.topoCustomCheck = [](const TopoInfoWithNetLayerDetails* topo) -> bool {
        if (topo->level0Topo == Level0Shape::MESH_1D_CLOS) {
            if (!topo->level0PcieMix) {
                bool isEqual = false;
                AutoSelectorBase::CheckMeshNumEqualToClosNum(topo, isEqual);
                return isEqual && topo->userRankSize <= 4;
            }
            return true;
        }
        return true;
    });

从上到下读：

  1. 最大拓扑层数设为1；结合TopoAttrs默认最小层数1，要求层数为1。
  2. 允许两类第0层形状。
  3. 声明支持PCIe混合，并要求相应场景的Mesh连通检查通过。
  4. 自定义检查在“混合形状且没有PCIe混合”这一分支中，还要求Mesh/Clos数量检查通过且rank数不超过4。
  5. 其他分支返回true，但仍须通过前面的公共检查及后续模型条件。

这里没有赋值的属性继续使用alg_attrs.h里的默认值。阅读属性注册时，必须同时看默认值，不能把“没有写”理解成“没有限制”。

11.2 第二步：模型管理器创建执行器

模型管理器根据目录中的算子类型和算法名执行：

auto exec = CollAlgExecRegistryV2::Instance().GetAlgExec(alg.opType, alg.algName);

它得到的是带有前面两个C++类型参数的执行器对象。接着：

auto params = exec->CalcCostCoeff(comm, topoInfo, alg.algName, param);

由于基类函数是virtual，这里会调用真实执行器类型的实现。这就是“通过统一接口调用不同算法的建模逻辑”。

11.3 第三步：执行器把拓扑转成模板建模参数

同一文件中搜索InsV2AllReduceSoleExecutor<...>::CalcCostCoeff。

该函数首先查属性，用TopoMatchOneLevel执行更具体的MatchTopo，取得算法层到物理层的映射。匹配失败则返回空数组。

随后读取rank数、网络类型、端口数量；端口数组为空也返回空数组。

最后核心调用是：

return InsAlgTemplate::CalcCostCoeff(CalcCostCoeffParam{
    rankSize,
    1.0f / rankSize,
    netTypeLevel0,
    BufferType::INPUT,
    BufferType::OUTPUT,
    BufferType::HCCL_BUFFER,
    portNumLevel0,
    isPod
});

此处的InsAlgTemplate已经在注册时绑定成InsTempAllReduceMesh1DOneShot。

CalcCostCoeffParam是一个参数结构体。花括号按字段顺序填入rank数、数据比例、网络类型、输入/输出/临时缓冲区角色、端口和Pod信息。这里的BufferType描述缓冲区角色，不是用户数据的FP32/FP16类型。

11.4 第四步：模板计算A/B/C/D

打开ins_temp_all_reduce_mesh_1D_one_shot.cc
src/ops/all_reduce/algorithm/template/aicpu/ins_temp_all_reduce_mesh_1D_one_shot.cc的CalcCostCoeff()。

第一条关键约束：

if (param.rankSize > 8) {
    return {};
}

即使前面拓扑属性检查通过，超过8个rank仍然拿不到该模板模型。

模板随后计算：

float n = param.dataRatio * param.rankSize;

执行器传来1/rankSize，所以这里得到n=1。同一个执行器还用于其他模板，因此OneShot在模板内部调整了传入的数据比例。

然后调用模型管理器的公共函数：

CalcMeshParam        → 得到跨卡传输系数A
CalcLocalCopyParams  → 得到本地拷贝系数B1
CalcLocalReduceParams→ 得到本地归约系数B2
B = B1 + (rankSize - 1) × B2
CalcLatencyParams   → 得到C
CalcLaunchParams    → 得到D

最后返回一个元素的数组{{A,B,C,D}}。这就成为这个算法的一段模型。

11.5 第五步：网络元数据与系数一起配合使用

执行器的GetAlgNetMeta()返回：

netTypes       = {该物理层网络类型}
groupSizes     = {1}
intraGroupMode = SUM
dataRatios     = {1 / rankSize}
rankSizes      = {rankSize}

模板内部用于构造系数的n=1，和元数据用于查利用率的dataRatio=1/rankSize，处在两个不同计算位置。应沿数据流分别理解，不能只看到两个比例不同就合并或替换。

11.6 第六步：本次代价表可能保留，也可能排除它

如果当前调用是AllReduce，并且通过数据类型、内存、保序等条件，它才会被算入当前表。

之后还要经过优先规则、可选Tuner和最小值比较。所以“算法注册成功”“模型计算成功”和“最终选中”是三个不同结果。

12. 沿着真实代码算一次代价

12.1 先规定算例前提

下面是按当前源码模型常数计算的教学算例，不是上板性能测试结果。假设：

  • 已进入新Selector普通路径，拓扑匹配和端口查询成功。
  • 4个rank，第0层是用于模型计算的1DMesh网络。
  • AllReduce、FP32、SUM，count=262144。
  • 本文OneShot算法没有被配置、其他属性或优先规则排除。
  • 不要求严格保序，未由Tuner覆盖cost。

这些前提用于说明它“如果进入代价表，会得到怎样的模型值”。不能由此断言它一定是该机器最终选中的算法。

12.2 算出数据量与A/B/C/D

数据量：

S = 262144 × 4 = 1048576B

执行器传入dataRatio=1/4，OneShot模板算出n=(1/4)×4=1。

对于Mesh，CalcMeshParam()中：

A = 1 / (56 × 10^9)
  ≈ 1.7857143 × 10^-11 秒/字节

这里输入缓冲区角色为INPUT，临时缓冲区角色为HCCL_BUFFER，两者不同，所以B包含本地拷贝项：

B = 1 / (750 × 10^9) + 3 / (483 × 10^9)
  ≈ 7.5445135 × 10^-12 秒/字节

模板设kernelNum=1，因此：

C = 1 × 2微秒 = 2微秒

任务数来自源码辅助函数：

transTaskNum = 5 × (4 - 1) = 15
syncTaskNum  = 2 × (4 - 1) = 6
taskNum      = 15 + 6 × 2 + (4 - 1) = 30
D            = 30 × 0.5微秒 = 15微秒

12.3 查利用率并计算分段代价

网络元数据的数据比例为1/4：

perTransferSize = 1048576 / 4 = 262144B

Mesh利用率表第一个上界是1MiB，262144B命中这一档：

util = 0.7135

带入公式：

跨卡部分 = A / util × S ≈ 26.2433微秒
本地部分 = B × S        ≈ 7.9110微秒
固定部分 = C            = 2微秒

segCost ≈ 36.1543微秒
cost = max(segCost, D)
     ≈ 36.1543微秒

数值经过四舍五入；程序实际使用float，末位可能有小差异。代价表内部存的秒数约为0.00003615。

这个计算过程把4个文件串了起来：执行器负责传参数，模板负责组合系数，CostModelManager提供带宽/时延模型，CostTableManager代入本次数据量。

12.4 再演示一次“比较并选中”

下面为了说明选择逻辑，候选X/Y及其数值完全是假设，并非仓库真实算法名或测量值：

当前候选 cost 结果
本文OneShot算法 约36.15微秒 有效，参与比较
候选X 28微秒 有效，目前最小
候选Y -1 无效，跳过

假设表就是这三项，结果选X。若Tuner把OneShot的cost改为0，就改选OneShot。若某个优先规则在Tuner之前已把X排除，Tuner拿到的表里就不会有X。

12.5 为什么改数据量可能换算法

为了单独观察数据量影响，再构造两条教学曲线，设u=S/1MiB：

算法P：tP = 5 + 20u 微秒
算法Q：tQ = 20 + 5u 微秒
数据量 P Q 较小者
0.1MiB 7微秒 20.5微秒 P
1MiB 25微秒 25微秒 相等
4MiB 85微秒 40微秒 Q

P启动轻，随数据量增长快；Q启动重，但大数据增长慢。这解释了为什么同一通信域模型可以复用，最终算法仍可能随着数据量变化。真实模型还包括查表档位、D项和各类过滤，曲线不一定如此简单。

13. 选完以后如何执行和回退

13.1 从字符串变回执行器

Selector()拿到结果后，会检查算法名、设置通信引擎、按需准备Kernel、设置算法资源标签等。

HcclExecOp()中再次通过注册表创建执行器：

auto executor = CollAlgExecRegistryV2::Instance().GetAlgExec(param.opType, algName);

建模时创建执行器，是为了调用CalcCostCoeff()和GetAlgNetMeta()；执行时创建执行器，是为了资源处理与算法运行。注册的是创建函数，不应把注册表理解成只保存一个永远复用的运行对象。

后续通过HcclGetAlgRes()等准备或复用资源，再根据不同引擎进入对应执行路径。Selector返回成功并不表示数据传输已经完成。

13.2 三种不同的“回退”

场景 发生位置 含义
特殊场景改为AIV_ONLY SelectorEngine::Run开头 开始建模/选择前改变允许的引擎范围
候选引擎中选到其他引擎算法 SelectMinCost 同一轮竞争产生的选择结果
资源或CCU协商导致重新选择 FallbackOp/ReSelector等 已经进入后续流程，再降低配置或按协商结果重选

这些机制不能混成“新Selector失败就跑旧Selector”。普通新旧分支没有这种自动失败回退。

13.3 ReSelector做什么

ReSelector()把传入的executeConfig写到param.opExecuteConfig，复用已有拓扑，再按同样的新旧开关条件选择。

新路径因为模型标签包含执行配置，会取得该配置对应的模型。

在满足编译版本条件的FallbackOp()中，CCU回退链是CCU_MS → CCU_SCHED → AICPU_TS；较低编译版本分支直接指定AICPU_TS。外层还有回退结果缓存和CCU参数协商路径，所以不能只看一次Run()日志就认定最终实际执行算法。

Selector()与ReSelector()还会检查通信域原始AIV_ONLY约束：如果实际引擎不是AIV，则返回不支持。

14. 如何理解配置和扩展点

14.1 三个配置不要混淆

配置 影响什么
HCCL_USE_NEW_SELECTOR 是否使用新选择流程
通信域算子展开模式/opExecuteConfig 初始执行机制及允许的候选引擎范围
通信域算法配置/HCCL_ALGO 在模型中进一步匹配或排除算法

FilterCmByHcclAlgo()优先读取通信域算法配置；为空或查询失败时，再尝试环境变量HCCL_ALGO。

当前解析器能识别例如：

export HCCL_USE_NEW_SELECTOR=1
export HCCL_ALGO='allreduce:sole{meshoneshot}'

这段示例的语法含义是“AllReduce，Sole执行组织，MeshOneShot模板方案”，不是直接填入C++类名。解析器与过滤实现见alg_parse.cc
src/common/alg_parse.cc。

但正向配置没有匹配到当前模型中的候选时，不能一概理解为严格报错：ProcessMatchedResults()是在存在正向匹配结果时才排除同算子未匹配项。具体结果应看配置解析日志和最终代价表。入门时可以先只开启新Selector，观察默认候选，再研究算法配置。

14.2 如果以后需要加入一个新算法，检查哪些连接点

这里解释扩展位置，不对仓库做代码修改。

  1. 执行实现：算子目录中的执行器和算法模板能够完成对应通信语义。
  2. 注册：执行器注册宏提供可创建对象的工厂，并登记算法目录。
  3. 属性：REGISTER_ALG_ATTRS声明正确的拓扑、数据类型及调用限制。
  4. 模型：执行器/模板提供适用范围内非空的CalcCostCoeff()，必要时提供多段GetAlgNetMeta()。
  5. 名称：与引擎、算子、执行组织和模板解析规则一致。
  6. 验证：既验证选择行为，也验证算法执行正确性和模型适用性。

最常见的断点是：执行器已有实现，但继承了基类默认返回空数组的CalcCostCoeff()，于是新模型构建时被跳过；或者登记了执行器，漏登记属性，在代价表阶段被过滤。

如果以后真的修改代码，新官方算子按src/ops/<op>/selector和algorithm/{executor,template}组织；试验性社区算子放在experimental/ops/<op>/。跨仓调用继续遵守HCCL/HCOMM动态加载边界。

15. 容易被名称和注释误导的地方

这些是本次对照实现确认的阅读要点，尤其适合读代码时回查。

容易产生的理解 当前实现应怎样读
头文件写“仅支持三个算子” .cc中的实际白名单有15种，以实现为准
FilterCmByEngine注释写count=-1 函数实际赋值0；表生成跳过小于等于0的条目
GetEnginePriority就是严格从前到后选引擎 过滤阶段按集合成员资格处理，最终比较有效候选cost
新流程只有公式，没有规则 属性、自定义回调、拓扑/算子优先规则都能改变候选集合
interGroupMode=MAX一定使组间取最大 当前计算代码组间仍执行cost += groupCost
所有数据量都读取param.inputSize 代价表使用CalcCostTableDataSize()，Tuner调用使用inputSize
Tuner的数据类型处理与代价表完全相同 代价表有统一GetOpDataType()；Tuner调用点目前只显式修正AlltoAll系列
uncalibrated一定是缺实测数据 也可能是拓扑不匹配、模板不支持当前rank数而返回空
没有属性也能通过拓扑检查，所以能参与竞争 缺属性的拓扑检查默认通过，但代价表会明确跳过无属性条目
注册时没写属性就没有限制 默认属性仍有效，例如默认拓扑形状、保序支持值等
一次新选择失败会自动进入旧选择器 该分支通过CHK_RET直接返回错误
Tuner日志说“未修改/忽略修改”就一定恢复了旧表 当前插件收到的是原表指针，调用失败分支没有备份恢复；插件实现应遵守契约

缓存也要按代码读：模型上下文的标签包含执行配置，AlgNetMetaRegistry则是按算法名保存元数据的全局注册表。不要因此宣称所有与拓扑有关的数据都完整隔离在每个通信域中；判断跨通信域使用行为需要继续分析对应实现。

本文侧重解释当前代码，不把上述差异扩展成未经测试的故障结论，也不尝试在教学文档中修复它们。

17. 自测题与答案

1. Selector返回HCCL_SUCCESS，是不是说明AllReduce已经算完了？

不是。表示选择阶段成功，之后还要准备资源和执行通信。

2. CostModel和CostTable有什么区别？

模型保存算法的估时系数；表保存针对当前调用得到的候选与cost。进入Run()后模型可缓存复用，当前表重新生成。

3. cm.costAlgoParams[i].count=0是不是把用户数据清空了？

不是。它让该模型算法条目不进入后续表，不修改用户数据个数。

4. 从CCU_MS进入，最终选到Aicpu算法，可能正常吗？

可能。候选集合允许AICPU_TS，最终按过滤后、经可选Tuner修改的cost比较，并更新执行配置。

5. 算法已经注册，为什么仍不出现在最终表里？

可能拓扑不符、模型为空、没有属性、引擎不在候选集合、算法配置排除、本次数据条件不符，或被优先规则排除。按阶段查证。

6. 两个算法cost相等，会选名字较小的那个吗？

当前循环保留表中先出现的那个，没有在这里按名字排序。

7. cost=max(segCost,D)中的D能直接加进segCost吗？

不能，那会改变当前模型。多段时也是先累加D，再和通信侧聚合结果取最大。

8. 设置HCCL_USE_NEW_SELECTOR=1后，为什么日志里还是没有Run？

先检查当前进程是否读取了配置，再检查兼容分流、零数据、单rank、缓存/快速启动、算子白名单以及算法插件快速路径。

9. 想看懂一个新算法，优先看哪几处？

执行器注册、属性注册、执行器CalcCostCoeff()、模板CalcCostCoeff()、GetAlgNetMeta()，最后回到公共CalcAlgCost()与实际执行入口。

10. 如何用自己的话完整描述新Selector？

“先取得当前调用参数和拓扑；根据注册算法建立适合该通信域与执行配置的模型；每次调用再筛选能力条件并计算代价，可选地让Tuner调整；从有效候选中选择最小值，输出算法名和执行配置，再交给后续资源与执行流程。”

本文通过本地源码静态阅读核对流程和接口，并对算例做了独立数值计算。没有运行NPU通信程序，因此不包含上板正确性结论或实测性能数据。
