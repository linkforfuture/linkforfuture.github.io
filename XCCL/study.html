1All-to-All 基础

每个节点和所有节点交换数据的最基础集合通信：4 卡时数据流共 n²=16 条，本质是对数据矩阵做一次“转置”。

图中虚线圆点会流动，表示数据包方向（若看不到动画，直接打开 alltoall.svg 即可）

要点速记
  • 发送方把本地数据切成 n 份，各发一份给所有 n 个接收方（包括自己）；接收方从 n 个来源各收 1 份。
  • 颜色 = 目标卡；每个分片上的 →j / 来自r 标明了去向与来源。
  • 与 Broadcast / Reduce 的区别：All-to-All 既发又收、且数据发生重排。
  • 每对卡数据量相等叫 alltoall；不等（如 MoE 的 token 路由）叫 alltoallv。

2GPU 与 SM

SM（Streaming Multiprocessor）是 GPU 的“核”：整卡由几十上百个 SM 组成，每个 SM 内含 Warp 调度器、CUDA core、共享内存与寄存器堆；kernel 被切成线程块分发给各 SM 执行。

整卡（H100 132 个 SM）→ 放大一个 SM → kernel 到线程块到 SM 的执行流程

要点速记
  • 层级：GPU → GPC → SM → CUDA core（“小兵”）。H100 有 132 个 SM，A100 108 个。
  • 调度单位：1 Warp = 32 个线程，由调度器整组发射、整组执行。
  • kernel 被切为线程块，GigaThread 按占用率分发给 SM；占用率受共享内存 / 寄存器 / Warp 上限共同限制。
  • 关键推论：一个 kernel 通常只占部分 SM → 同一张卡上可并发多个 kernel —— 这正是 DeepEP 能重叠通信与计算的硬件前提。

3DeepEP 如何优化 All-to-All

MoE 里的 all-to-all 是 dispatch（token 发给专家所在卡）+ combine（部分结果收回求和）。DeepEP 用 SM 分区把通信压到 4~6 个 SM 上、再跨 micro-batch与专家计算错位重叠，把通信从“串行停顿”变成“隐藏成本”。

背景（dispatch/combine）→ 优化① SM 分区 → 优化② 跨 micro-batch 时间线重叠 → 其余工程

要点速记
  • 通信 kernel 只占 4~6 个 SM，其余 SM 全给专家 FFN → 同一张卡内并行。
  • 重叠的永远是不同 micro-batch 的数据：dispatch(mb[i+1]) ∥ FFN(mb[i])、combine(mb[i-1]) ∥ FFN(mb[i])。
  • 依赖约束必须满足：dispatch(mb[i]) 先于 FFN(mb[i])；combine(mb[i]) 晚于 FFN(mb[i])。
  • 其余工程：零拷贝（NVLink 直访对方显存）、NVLink + RDMA 两阶段转发、FP8 带宽减半、低延迟 decode kernel。
  • 这是 overlap（两个 kernel 并发），不是 fusion（合成一个 kernel）；combine 里的“接收 + 求和”算是融合。

4通算重叠的通用模式

DeepEP 只是“把等数据藏进处理别的数据”这个通用套路的一个实例。抽象成“取数据 → 处理 → 送出”三级流水线后，CPU 预取、CUDA 双缓冲、训练流水线、DeepEP 是同一个套路的四个面孔。

上半：抽象流水线三级错位；下半：四个具体系统与抽象模式的对应

要点速记
  • 口诀：Fetch(i+1) ∥ Process(i) ∥ Send(i-1) —— 三者各忙各的数据，互不等待。
  • 四实例对照：CPU 预取、CUDA 双缓冲、训练流水线（forward/backward）、DeepEP（dispatch/FFN/combine）。
  • 代价：需要 ≥2 份数据在飞（内存翻倍），流水线首尾有填充/排空气泡。
  • 一句话：把“数据还没到”的空档，用“处理另一份数据”填上 —— 这就是 overlap 的秘密。

5Prefill · Decode · KV Cache 概念

一次请求分两段：Prefill 并行算完整段 prompt（计算密集）并产出 KV cache；Decode 逐 token 自回归生成（访存密集），每一步都要读 KV cache。KV cache 是这两个阶段之间的“交接货物”。

上半：一次请求的生命周期；下半：三张概念卡

要点速记
  • Prefill：并行处理整段 prompt，计算密集、突发到达；产出第一个 token + KV cache；指标看 TTFT。
  • Decode：逐 token 自回归，访存密集、每步读几 GB KV；延迟敏感；指标看 ITL / TPOT。
  • KV cache：本请求各 token 的 K/V，按 请求 × 位置 × 层 × head 记录；随 并发 × 上下文长度增长，与词表无关。
  • 为什么要缓存：decode 每步都要对全部历史做 attention，缓存免去每步重算整段历史。

6KV Cache 通信加速

KV cache 是分布式推理里通信原语要搬的“持久载荷”：大（GB/请求）、持久、首包延迟敏感、有序可流式、可压缩。三个通信形态（分离 / 环 / 池）+ 三条加速轴（搬得快 / 少搬 / 重叠）。

左：载荷特殊性 → 中：三条加速轴 → 右：三个通信形态与各自加速手段

要点速记
  • KV cache 是通信载荷：大（128K 上下文 ≈ 40 GB）、持久、首包延迟敏感、有序可流式、可压缩。
  • 三个形态：分离式（p2p / RDMA write）、上下文并行（环上 p2p）、池化（远端 RMA）。
  • 三条加速轴：搬得快（零拷贝 / 多 NIC 聚合）、少搬（压缩 / 前缀复用 / 搬 Q 不搬 KV）、重叠（藏进计算）。
  • 生产实例：Mooncake TE（40GB KV 到 87/190 GB/s，比 TCP 快 2.4×/4.6×）、Ring Attention / CP、CacheGen（带宽降 3.7~4.3×）。
