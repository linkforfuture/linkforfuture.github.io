两个维度逐步归约，

ReduceScatter Parallel 把每个 rank 的数据沿 Level 0 与 Level 1 两个维度分两步归约、分散； AllReduce Parallel 则在它后面再接两个 AllGather 阶段，沿相反路径把结果收回来。 这篇笔记逐阶段数清每个 rank 持有多少、发给谁、发多少字节。

01

为什么这两个算子可以放在一起看

AllReduce = ReduceScatter + AllGather，而这里连路径都是镜像的

ReduceScatter 的目标是「归约完再分散」：每个 rank 输入 P·d 字节， 输出 d 字节，且这 d 字节对应的是某一个目标 rank 的数据块，里面已经集齐了全部 P 个 rank 的贡献。

AllReduce 的目标是「归约完还要人手一份」：输入输出都是 S 字节。 最自然的实现就是先按 ReduceScatter 的方式把数据归约并散开，再沿相反的顺序把结果收集回来 —— 这正是 AicpuAllReduceParallelMeshNHR 做的事。

最直接的证据：AllReduce 的执行器一次性注册了四个模板
  • ReduceScatter 侧只注册两个：InsTempReduceScatterMesh1D 与 InsTempReduceScatterNHR。
  • AllReduce 侧注册四个，横跨两个算子的模板家族：两个 ReduceScatter 模板 + InsTempAllGatherMesh1D + InsTempAllGatherNHR。
  • 也就是说，「RS 两阶段 + AG 两阶段」不是我们的比喻，而是源码里的模板装配方式。见 §10 的注册片段。

注意「反向」具体指什么：对 A 片，ReduceScatter 的顺序是 Mesh → NHR， 而 AllGather 的顺序是 NHR → Mesh；B 片同理，两条路径各自把顺序倒过来。 这不是巧合：归约是「先拆开、后合拢」，收集就必须「先合拢、后拆开」。

02

统一口径与 ρ 语义

先把统计边界和配置含义对齐，后面的数字才有意义

沿用二维拓扑：Level 0 大小为 M（Mesh / 同一 j 沿 i 方向）， Level 1 大小为 N（NHR / 同一 i 沿 j 方向），总 rank 数 P = M·N， rank 编号 r = j·M + i。源码里对应 rankIdxLevel0_ = myRank % M、rankIdxLevel1_ = myRank / M。

统计口径

本文统计的是每 rank 的网络有效载荷发送量，包含中间结果的转发，不计协议开销、通知和本地拷贝。 在等长分片下收发量相等，所以只报发送量。

ρ 的含义：两个算子族的约定是相反的

这是读源码时最容易踩的坑。配置项 multipleDimensionSplitRatio 在 ReduceScatter / AllReduce 里表示先 Mesh 的那一份，在 AllGather 里却表示先 NHR 的那一份。 本文用 ρ 统一表示本次两个算子的先 Mesh 比例。

ρ 到底从哪里来？优先级与默认值

优先级从高到低（op_common.cc:3748）：

  • 通信域配置 —— HcclSetConfig 下发的 HCCL_CONFIG_TYPE_MULTIPLE_DIMENSION_SPLIT_RATIO，来源标记 COMM_CONFIG。
  • 环境变量 —— HCCL_ALG_MULTIPLE_DIMENSION_SPLIT_RATIO（src/common/alg_env_config.cc:125），需为有限值且在 [0,1]，来源标记 ENV_CONFIG。
  • 内置公式 —— 都没配时来源标记为 BUILTIN_FORMULA，此时调用 CalcParallelDataSplitRatio 按端口带宽算，不是简单取 0.5。

内置公式的大意：mesh 侧时间系数 ≈ 21/20 · (M−1)/(M·intraPorts)， clos 侧 ≈ (N−1)/(N·interPorts/2)，取使两侧相等的比例， 再量化到 1/8 的整数倍并夹在 [1/8, 7/8]。0.5 只是公式失效时的回退值。

非末轮的 4K 对齐会让实际比例略微偏离配置值
两个算子在分循环（loop）时，只要不是最后一轮，part0 / part1 各自的字节数都会向下取整到 AICPU_ALIGN_SIZE（4096）； 余量滚到最后一轮用不齐的值，因此跨轮总量是精确的，但单轮的等效 ρ 会略小于配置值。 上一轮的余量集中在末轮处理，这是分循环实现的常规做法。
03

ReduceScatter：在每个目标块内部切分

切分粒度是这篇笔记里第二个容易搞错的地方

设每 rank 最终输出 d 字节，那么每 rank 输入是 P·d 字节，可以看成 P 个「目标 rank 的块」，每块 d 字节，块 t 落在 offset t·d。 记 Xs[t] 为源 rank s 对目标 rank t 的贡献，则最终 Yt = ⊕s Xs[t]，其中 ⊕ 是配置的归约操作。

切分发生在每一个目标块内部：Xs[t] = As[t] ‖ Bs[t]， 其中 a = ρd、b = (1−ρ)d。 于是每 rank 的输入里含有 P 个 A 片和 P 个 B 片，总量分别是 Pa 和 Pb。

实现上的一点出入，但净效果等价。代码是在每个 loop chunk 上做一次连续切分 （dataOffset0 = processedCount·itemSize、dataOffset1 = dataOffset0 + currCountPart0·itemSize）， 而「按块切」的语义是由模板的 stride 索引还原出来的： Intra0 用 inputSliceStride = d、inputRepeatStride = d·M， Inter1 用 inputSliceStride = d·M、inputRepeatStride = d。 两者配合，跨轮累积起来正好覆盖每个块的 A 段和 B 段。
别把 d 和 D 搞混
ReduceScatter / AllReduce / AllGather 三个算子里，dataCount_ 都是每 rank 的输出 count （ReduceScatter 侧由 param.DataDes.count = recvCount 而来）， 所以 d = dataSize_ = dataCount_ × dataTypeSize_ 是「一个目标块」的长度，不是整个 tensor。 每 rank 的输入是 P·d；全部 P 个 rank 的输出加起来才是 P·d。
04

ReduceScatter 的两阶段与流量账

A 片先横着走，B 片先竖着走，然后各自换方向

第一阶段：A 片在行内归约，B 片在列内归约。

  • A 片，Intra0 = Mesh ReduceScatter。同一行的 M 个 rank 归约，当前 rank 留下所有「目标列为 i」的部分结果，即目标 (0,i)…(N−1,i)，共 Na 字节。每份结果含本行 M 个源 rank 的贡献。
  • B 片，Inter1 = NHR ReduceScatter。同一列的 N 个 rank 归约，当前 rank 留下所有「目标行为 j」的部分结果，即目标 (j,0)…(j,M−1)，共 Mb 字节。每份结果含本列 N 个源 rank 的贡献。

第二阶段：沿另一维继续归约，只留下本 rank 的目标块。

  • A 片，Inter0 = NHR ReduceScatter。把各行对相同目标的部分结果归约，留下本 rank 的 a 字节。
  • B 片，Intra1 = Mesh ReduceScatter。把各列对相同目标的部分结果归约，留下本 rank 的 b 字节。
「同步」同步的是什么？是 PreSyncInterThreads / PostSyncInterThreads， 底层是控制线程与两个模板主线程之间的 HcommThreadNotifyRecordOnThread / HcommThreadNotifyWaitOnThread —— 线程间的通知，不是网络屏障。 它保证阶段 2 的两个模板不会在阶段 1 的数据就绪前启动；跨 rank 的数据可见性由通信语义本身保证。

每阶段流量

阶段操作每 rank 有效数据变化每 rank 发送量
1A 片 Mesh RSPa → Na(M−1)·Na
1B 片 NHR RSPb → Mb(N−1)·Mb
2A 片 NHR RSNa → a(N−1)·a
2B 片 Mesh RSMb → b(M−1)·b

第一阶段的放大倍数直接对应代码里的模板参数：Intra0.repeatNum = N（即 rankSizeLevel1_）、 Inter1.repeatNum = M（即 rankSizeLevel0_），第二阶段两者都是 1。 TemplateDataParams::repeatNum 就是「同一套收发要重复几遍」。

两个维度累计发送量（每 rank，单位字节）
VMesh = (M−1) · (Na + b)
VNHR = (N−1) · (Mb + a)
VRS = VMesh + VNHR = (P−1)·d = (P−1)/P × 每 rank 输入量

守恒可以展开验证：把 Na = Nρd、Mb = M(1−ρ)d 代入， ρ 的系数项正负抵消，只剩 (M−1) + M(N−1) = MN − 1 = P − 1。 换句话说：无论 ρ 取多少，总发送量恒定，ρ 只决定这笔流量在两个维度之间怎么分。

M = N = 2 的 r0 走查

第一阶段结束后，r0 手里是两份部分结果（都以本行 / 本列的贡献为初值）：

  • A 片（目标列 i = 0，即 r0 与 r2）： A_r0[r0] ⊕ A_r1[r0]、A_r0[r2] ⊕ A_r1[r2]，共 Na 字节。
  • B 片（目标行 j = 0，即 r0 与 r1）： B_r0[r0] ⊕ B_r2[r0]、B_r0[r1] ⊕ B_r2[r1]，共 Mb 字节。

第二阶段：r0 从 r2 拿到目标 r0 的另一行 A 片贡献，从 r1 拿到目标 r0 的另一列 B 片贡献， 归约后拼成自己的完整输出 [A ‖ B]，正好 d 字节。

把 M = N = 2 代进公式：V_Mesh = (1)(2a + b) = 2ρd + (1−ρ)d， V_NHR = (1)(2b + a) = 2(1−ρ)d + ρd，两者相加 = 3d = (P−1)d ✓

表里的「有效数据」指后续仍需处理的结果量。原始 input 和 scratch 里的旧数据不一定被清除 —— 别把它当成内存回收。

05

AllReduce：RS → RS → AG → AG

前两阶段归约并散开，后两阶段把结果收回来

AllReduce 每 rank 输入输出都是 S 字节（当前循环内）。这里的口径和 ReduceScatter 不同： A = ρS、B = (1−ρ)S 是整个输入区域的两段连续数据， 而不是「每个目标块内部」的切分 —— S 本身就等于 P·d。

阶段A 片路径B 片路径此时数据包含的贡献
1Mesh RS → A/MNHR RS → B/NA 含本行贡献；B 含本列贡献
2NHR RS → A/PMesh RS → B/P每份留下的数据均已完成全局归约
3NHR AG → A/MMesh AG → B/N传播已归约的结果
4Mesh AG → ANHR AG → B每 rank 获得完整 AllReduce 结果

每阶段流量

以下按均匀分片计算；实际尾片要用源码的 sliceSize / tailSize，见 §9。

阶段Mesh 每 rank 发送量NHR 每 rank 发送量
1 · 第一次 RS(M−1)·A/M(N−1)·B/N
2 · 第二次 RS(M−1)·B/P(N−1)·A/P
3 · 第一次 AG(M−1)·B/P(N−1)·A/P
4 · 第二次 AG(M−1)·A/M(N−1)·B/N
AllReduce 每 rank 累计发送量
VMesh = 2(M−1) · (A/M + B/P)
VNHR = 2(N−1) · (B/N + A/P)
VAR = 2 · (P−1)/P × S

同样可以把 ρ 消掉：把 A = ρS、B = (1−ρ)S 代入后， ρ 的两个系数都等于 (P−1)/P，而它们的权重之和是 ρ + (1−ρ) = 1， 所以总量与 ρ 无关。这也解释了为什么 AllReduce 的流量正好是 ReduceScatter 的 2 倍： 2(P−1)/P·S 而 RS 是 (P−1)/P·S —— 一次归约 + 一次收集。

06

分片所有权：路径决定布局

阶段 2 结束后，谁手上拿着哪一块？

AllReduce 内部的分片所有权由路径决定。在均匀切分下，对 rank (j,i)：

  • A 片先按 M 分块、再按 N 分块，所以 (j,i) 持有 A 片的第 i·N + j 个小块。
  • B 片先按 N 分块、再按 M 分块，所以 (j,i) 持有 B 片的第 j·M + i 个小块。

源码里就是两个一眼能看懂的函数：CalcRankIdInter(i,j,part2) = i·part2 + j（A 的映射）、 CalcRankIdIntra(i,j,part1) = j·part1 + i（B 的映射）。

随后 r0 先通过列内 NHR 收齐 (A₀, A₁)、 通过行内 Mesh 收齐 (B₀, B₁)， 最后再沿另一维收齐完整 A、B。这个映射来自 FillDataMap 与两个 CalcRankId* 函数。

07

归约发生在哪里

两个算子复用同一组 ReduceScatter 模板，但两条路径的归约方式完全不同

这是性能建模时最容易漏掉的一块：网络流量不是全部成本。Mesh 路径有明确的本地归约开销， NHR 路径则有逐轮的收发 + 归约开销。

对称内存路径（symmetric memory）会走另一套

开启 supportSymmetricMemory 后，归约直接在 input 上就地进行 （mesh 用 SendRecvBatchReadReduce、NHR 用 SendRecvBatchReadReduce 读对端窗口 + 就地归约）， 省掉「写对端 buffer」和「本地预拷贝」两次搬运。

AllReduce 在此基础上，阶段 2 与阶段 3 之间还有一次 LocalCopy： 把本 rank 的归约结果从 input 搬到 output，供两个 AllGather 阶段使用； AG 阶段的 outBuffType 是 OUTPUT 并打开 enableRemoteMemAccess，直接读对端的 output 窗口。

顺带一个副产品：对称内存路径下 sliceCount = dataCount_，不进入分循环， 一次做完 —— 这也是它和普通路径在性能模型上最大的差别之一。

普通 buffer 路径的数据演进

算子数据演进
ReduceScatterinput → CCL buffer → output
AllReduceinput → CCL buffer → CCL buffer → CCL buffer → output

AllReduce 中间那三段 CCL buffer 正好对应阶段 1/2/3 的产物；只有最后一个 AG 阶段把结果落到 output。 Scratch 的偏移也有讲究（A 在 offset 0、B 在不同 multiple 偏移），见 §10 的自测清单。

08

NHR 逐轮：ReduceScatter 与 AllGather 互为镜像

同一个 NHR，两个方向，公式上下标正好对调

对于 N 个参与 rank 的 NHR ReduceScatter，第 s 轮（s 从 0 开始）：

NHR ReduceScatter · 第 s 轮
Δs = 2s　　sendTo = (j − Δs + N) mod N　　recvFrom = (j + Δs) mod N
发送份数　qs = ⌊ (N − 1 + 2s) / 2s+1 ⌋
每轮发送量　Vs = qs · R · z　　（R = repeatNum，z = 单份大小）

而 NHR AllGather 是它的镜像：距离顺序反过来（从 2K−1 递减到 1）， 收发方向也对调。

NHR AllGather · 第 s 轮
Δs = 2K−1−s　　sendTo = (j + Δs) mod N　　recvFrom = (j − Δs + N) mod N
发送份数　qs = ⌊ (N − 1 + Δs) / (2Δs) ⌋
模板通信距离顺序每轮发送份数累计份数
NHR ReduceScatter1, 2, 44, 2, 17
NHR AllGather4, 2, 11, 2, 47
轮数是 ⌈log₂N⌉，不是 log₂N
源码用 GetNHRStepNum(N) 计算轮数，它数的是 N−1 的二进制位数，即 ⌈log₂N⌉。 只有 N 是 2 的幂时两者才相等。反例：N = 5 时是 3 轮，份数序列 (2,1,1)， 每轮至少发 1 份，累计仍是 Σqs = N−1 = 4。

时间模型与开销清单

ρ 不改变总量，那它到底在调什么？

既然总量与 ρ 无关，调 ρ 的唯一目的就是让两个维度的并行阶段耗时尽量相等 —— 每个阶段的耗时是 max(mesh, nhr)，一方闲着就是纯浪费。

ReduceScatter（两阶段串行）
T ≈ max( TMesh((M−1)Na), TNHR((N−1)Mb) )
　+ max( TNHR((N−1)a), TMesh((M−1)b) ) + Tsync
AllReduce（四阶段串行，每阶段两条路径并行）
T ≈ Σk=1..4 max( TMesh(stage k), TNHR(stage k) ) + 3·Tsync
INTERACTIVE · 切分比例

单位见下方读数

本文推导：三个「平衡点」并不重合

设两个维度带宽相同，令 Mesh 与 NHR 的总量相等，解出（三个算子形式完全一致）：

ρ* = (MN − 2M + 1) / [ 2(M−1)(N−1) ]，当且仅当 M = N 时等于 0.5。

但真正决定耗时的是每个阶段内部的 max，于是还有两个分阶段平衡点：

ρ₁ = M(N−1) / [ N(M−1) + M(N−1) ]（阶段 1：Na 对 Mb）
ρ₂ = (M−1) / [ (M−1) + (N−1) ]（阶段 2：b 对 a）

三者只有在 M = N 时才同时等于 0.5。 以 M=2, N=8 为例：ρ₁ ≈ 0.64、ρ₂ = 0.125、ρ* ≈ 0.93 —— 没有一个 ρ 能同时把两个阶段都配平，这也是源码最终改用端口带宽公式而非定值的原因。

以上是等带宽下的理想化推导，仅用于理解「ρ 在权衡什么」；实际取值以 CalcParallelDataSplitRatio 为准。

性能模型需要单列的本地开销

网络流量之外，还有这些
  • 本地拷贝 —— 普通路径的 input → CCL buffer、CCL buffer → output；对称内存路径的 input → output。
  • Mesh 本地归约 —— 接收端的 LocalCopy + LocalReduce，量级与收到的分片量同阶。
  • NHR 逐轮归约 —— 每轮都要把收到的分片 Reduce 进部分结果，共 ⌈log₂N⌉ 轮。
  • 阶段同步 —— ReduceScatter 1 次、AllReduce 3 次，量级不大但在小包场景不可忽略。
  • 非均匀尾片 —— sliceSize / tailSize 使各 rank 的实际数据量略有差异，末位 rank 可能更大。

自测清单

① 验流量守恒：为什么总量与 ρ 无关

ReduceScatter：代入 Na = Nρd、Mb = M(1−ρ)d

V = (M−1)d(1 + (N−1)ρ) + (N−1)d(M − (M−1)ρ)

　 = d[(M−1) + (M−1)(N−1)ρ + M(N−1) − (M−1)(N−1)ρ]

　 = d[(M−1) + M(N−1)] = d(MN − 1) = (P−1)d ✓

AllReduce 同理，ρ 的两个系数都化简为 (P−1)/P，权重和为 1。

② 验 NHR 份数公式：Σqs = N−1

qs = ⌊(N−1+2s)/2s+1⌋，轮数 K = ⌈log₂N⌉。

小规模手算：

  • N=4：q = (2,1)，和 = 3 ✓
  • N=5：q = (2,1,1)，和 = 4 ✓
  • N=8：q = (4,2,1)，和 = 7 ✓

直觉：第 s 轮结束时，每个分片已经合并了 2s+1 个源的贡献， 所以剩下的工作量按 2s+1 递减，总和自然收敛到 N−1。

③ 验分片所有权表（M = N = 2）

A 片映射 i·N + j：r0(j0,i0)→0、r1(j0,i1)→2、r2(j1,i0)→1、r3(j1,i1)→3 ✓

B 片映射 j·M + i：r0(j0,i0)→0、r1(j0,i1)→1、r2(j1,i0)→2、r3(j1,i1)→3 ✓

与图 7 对照，两张表完全吻合。

④ 容易被公式掩盖的边界
  • 「A/M」不是真的除法 —— GenDataParamsAllRank 里先 RoundDown 到数据类型大小的整数倍，余量给最后一个 rank（tailSize），尾片可能比 sliceSize 更大。
  • 分循环 —— sliceCount 受 CCL scratch 与 UB_MAX_DATA_SIZE 限制，loopTimes = ceil(dataCount_/sliceCount)，余量摊到剩下的轮次。
  • 对称内存不分循环 —— sliceCount = dataCount_，一次做完。
  • 数据类型限制 —— 基础注册不支持 64 位类型（INT64/UINT64/FP64）和 PROD；CCU 变体另外排除 INT8 和 inplace；MultiJetty 变体不支持对称内存。所以上面的公式永远不适用于 64 位数据。
  • 命名有坑 —— CalcIntraDataAllRank 填的却是 rankBaseOffInterAGMap_，反之亦然；模板名里的 Intra/Inter 指 server 内 / server 间。
