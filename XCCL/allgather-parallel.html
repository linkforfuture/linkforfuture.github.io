01 / START WITH THE PICTURE

两片数据，
两条路同时走

AllGather 要把每个 rank 的数据送到所有 rank。当机器天然分成两个维度时，HCCL 的 Parallel 执行器会把数据切成两片，一片先 Mesh 后 NHR，一片先 NHR 后 Mesh，让两条链路同时忙起来。

这篇文章不满足于"知道它并行"，而是把账算清楚：每个阶段，每个 rank 手上握着多少数据、发给谁、发多少字节。

7 张图解，全部 SVG 手绘流量公式可自行复算附可拖动的切分比例模型

先明确 AllGather 要什么

设共有 P 个 rank，每个 rank 的输入是 D 字节。AllGather 结束后，每个 rank 的 output 里都完整地排着全部 P 个 rank 的数据，共 P·D 字节。

注意这个语义里没有"归约"——数据只是被复制、搬运、排好位置。所以 AllGather 的代价几乎全部由搬运次数和走哪条链路决定。

为什么"并行"能省时间

如果只用一条链路（比如全走 Ring，或者全走 NHR），那么每个 rank 至少要承担 (P−1)·D 的发送量，而且这些字节要挤在同一条链路上排队。

但真实的机器往往有两级连接：机器内部的高速互联，和机器之间的网络。它们是两条物理上独立的链路，可以同时传输。Parallel 执行器的想法很直接：

一句话理解 Parallel
  • 把本次数据切成 A 片 和 B 片。
  • A 片先在第一个维度上收齐，再整块沿着第二个维度传播。
  • B 片反过来：先在第二个维度上收齐，再整块沿着第一个维度传播。
  • 两个方向的两步在时间上是并行发起的，所以两条链路同时在传数据。

代价是什么？总发送量并不会变少——仍然是每 rank (P−1)·D。Parallel 换来的不是"传得更少"，而是"把流量摊到两条链路上，让总耗时由较长的那条决定，而不是两者相加"。这个问题在第 09 节还会再算一次。

02

把 P 个 rank 摆成一个 M×N 的网格

并行执行器的两个维度，来自拓扑的两层结构。

Parallel 执行器用一个二维视角描述通信域，把参与通信的 rank 排成网格：

两个维度的定义
  • Level 0，大小 M：同一行内的 rank 之间做 Mesh（全连接，互相直接读）。
  • Level 1，大小 N：同一列内的 rank 之间做 NHR（逐轮递归减半，多跳转发）。
  • 总 rank 数 P = M × N，rank 编号 r = j × M + i，其中 i 是 Level 0 内的编号（列号），j 是 Level 1 内的编号（行号）。

图 1 · 二维拓扑。行方向（Level 0）用 Mesh，每两个 rank 之间双向直达；列方向（Level 1）用 NHR，靠多轮转发。图中取 M=3、N=2 便于看清编号规则，i 变化让 rank 号 +1，j 变化让 rank 号 +M。

为什么要关心"谁是低位"？因为 r = j × M + i 这个约定决定了同一个 Level 0 行里装的是哪几个 rank。在实际硬件上，这通常对应"同一台机器内的几张卡"或者"同一个超节点内的几个 rank"。哪条链路快，就应该让哪一维承担更多的数据——这正是下一节要切分的理由。

03

把本次数据切成 A、B 两片

切分比例是一个可配置的量，它决定两条链路各背多少流量。

执行器把本 rank 本次要处理的数据切成两段：

片与长度
Xj,i = Aj,i ‖ Bj,i ,　　a + b = d
a = (1 − ρ) · d　　（A 片长度）
b = ρ · d　　　　（B 片长度）

其中 ρ 就是配置项 multipleDimensionSplitRatio，它表示 B 片的比例，也就是代码注释里的"数据片 1"。

这里有两个容易混淆的量，先分清楚：

符号含义代码对应
D单个 rank 的数据块大小，也是 output 里分给每个 rank 的槽位长度dataSize_ = dataCount_ × dataTypeSize_
d本次循环处理的数据量。D 很大时会被切成若干块依次处理currCount × dataTypeSize_

别把 D 当成"整个 tensor"。它是一个 rank 的数据量。全部 P 个 rank 的数据加起来是 P·D，那也正是每个 rank 最终 output 的大小。

ρ 从哪里来？取值优先级是：通信域配置 HCCL_CONFIG_TYPE_MULTIPLE_DIMENSION_SPLIT_RATIO ＞ 环境变量 HCCL_ALG_MULTIPLE_DIMENSION_SPLIT_RATIO ＞ 默认 0.5。此外还有一个"比例来源"开关 multipleDimensionSplitRatioSource_，默认取 BUILTIN_FORMULA：此时执行器并不直接采用配置里的数字，而是先用内置公式算出"先 Mesh 后 Clos"那一片的比例，再取补得到 ρ。

图 2 · 数据切分。两片的长度由 ρ 决定，两片的路径是固定互反的。ρ=0.5 是图中画出的均分情形，实际取值远不止 0.5 一种。

三个容易忽略的实现细节：

  • 元素取整。a、b 最终要落到"多少个元素"上：currCountPart0 由 比例 × currCount 截断取整得到，currCountPart1 直接取余下的部分。所以本文的公式是忽略取整的连续近似，真正参与通信的是 currCountPart0 / currCountPart1 乘以数据类型字节数。
  • 非末次循环的 4K 对齐。只要不是本轮循环的最后一块，两片都会各自向下对齐到 4096 字节（且只在片本身 ≥ 4K 时才对齐）。
  • 对齐会"滚存"。因为是对齐取整，非末次循环里 part0 + part1 会略小于 currCount，这个差额会累积到末次循环一起处理。所以严格等于 (P−1)·D 的是跨循环的累计值，而不是单次循环。
04

两个阶段：每条路各走两步

阶段内两项操作并行，阶段之间有同步。

整个执行过程被切成两个阶段。每个阶段里，两个维度上的操作同时发起：

图 3 · 两阶段数据流。注意 A 片和 B 片在两个阶段里走的是同一条链路的不同方向：A 片先在 Mesh 上收齐、再在 NHR 上扩散；B 片反过来。

为什么必须是这个顺序

关键在于阶段 2 传播的数据量会变大。第一阶段结束时，A 片从 a 膨胀成 M·a（本行所有 rank 的 A 片），B 片从 b 膨胀成 N·b（本列所有 rank 的 B 片）。

第二阶段要做的，是把这两个"已经变大的块"沿着另一个维度整体扩散出去。实现上用 repeatNum = M 或 repeatNum = N 来描述这些数据片——它们在 output 里可以是跨步分布的，不要求先打包成一块连续内存。

"同步"同步的是什么

阶段之间的同步不是网络 barrier，而是线程间的通知。两个模板各自跑在独立的线程上（一个负责 intra/Mesh，一个负责 inter/NHR），主线程按顺序提交两项任务后由它们并行执行，再通过一对 notify record / wait 与两个模板线程对齐；跨 rank 的同步则由模板内部的通信自己完成。

每个阶段的内外结构因此是：前置同步 → 提交两项任务 → 后置同步。阶段 1 先提交 A 片（Mesh）再提交 B 片（NHR）；阶段 2 先提交 A 片（NHR）再提交 B 片（Mesh）。提交顺序不等于执行顺序——真正决定谁先跑完的是两条链路的实际速度。

循环处理：上面的 d、a、b 都是"一次循环"的量。外层是一个 while (processedCount < dataCount_) 循环：先按 ceil(dataCount_ / maxCountPerLoop) 算出总轮数，每轮再按剩余轮数均分当前剩余量，并用 maxCountPerLoop 封顶。其中 maxCountPerLoop = min(scratchMemBlockSize, UB_MAX_DATA_SIZE) / dataTypeSize_——即缓冲区能容纳多少元素就一轮传多少；若开了对称内存，则直接一次传完。

每一块都完整走一遍上面的两个阶段。所以整个 tensor 处理完，每个 rank 的累计发送量是 (P−1)·D——这一点和用哪种切分比例无关。

06

流量账本：每条链路各发多少

把四个阶段的发送量加起来，看看总账是不是守恒。

下面统计的是有效载荷的单向发送量：每个 rank 发出的字节数。接收量与之相等。这里包含转发的数据，但不计协议头、通知消息和本地拷贝。

阶段操作链路每 rank 发送量
1A 片收齐本行Mesh(M − 1) · a
1B 片收齐本列NHR(N − 1) · b
2A 片扩散到全列NHR(N − 1) · M · a
2B 片扩散到全行Mesh(M − 1) · N · b
按链路归并
VMesh = (M − 1)(a + N·b) = (M − 1)·[ 1 + (N − 1)·ρ ]·d
VNHR　= (N − 1)(b + M·a) = (N − 1)·[ M − (M − 1)·ρ ]·d
Vsend = VMesh + VNHR = (M·N − 1)·d = (P − 1)·d

最后一行很有意思：两条链路的流量加起来恒等于 (P−1)·d，与 ρ 完全无关。也就是说，调切分比例不会减少总搬运量，它只是把同样的字节在两条链路之间挪来挪去。

方向也很直观：ρ 越大（B 片越多），Mesh 的流量越大、NHR 的流量越小。因为 B 片是"先在 Level 1 收齐、再由 Level 0 扩散"的那一片。

交互实验 · 本节流量模型

拖动 ρ，看流量怎么搬家

单位：d（本次数据量）
P = M × N4
Mesh 流量 VMesh1.50 d
NHR 流量 VNHR1.50 d
ρ = 0.50：两条链路的发送量相等。

图为本节推导出的解析模型，不是实测性能。它只回答"发多少字节"，不含带宽、轮次同步与竞争开销。

一个可以自己推的结论
  • 令 V_Mesh = V_NHR，解得流量均衡点 ρ* = (M·N − 2M + 1) / [ 2(M − 1)(N − 1) ]。
  • 只有当 M = N 时，ρ* 才等于 0.5。M ≠ N 时，均衡点会明显偏移。
  • 例如 M=2, N=8 时 ρ* ≈ 0.93；M=8, N=2 时 ρ* ≈ 0.07。上面拖动滑块就能看到交点移动。

但要小心：流量相等 ≠ 时间相等。Mesh 和 NHR 的带宽、启动开销、轮次同步成本都不一样。要让两条链路同时做完，ρ 还要按两条链路的实际能力反比偏移。这才是切分比例值得做成配置项的原因——见第 09 节。

07

NHR 内部：一轮到底发几份

把 Level 1 那条路拆开，看它怎么用 log₂N 轮把数据铺开。

Level 1 的传播由 NHR 完成。设一次 NHR 有 N 个参与 rank，算法内编号为 j，则轮数为 K = ⌈log₂N⌉。第 s 轮（s = 0 … K−1）：

第 s 轮
Δs = 2K−1−s　　　　（本轮通信距离，逐轮减半）
sendTo = (j + Δs) mod N　　　recvFrom = (j − Δs + N) mod N
qs = ⌊ (N − 1 + Δs) / (2·Δs) ⌋　　（本轮发送的数据份数）
发送的源 rank 依次为：j, j − 2Δs, j − 4Δs, … (mod N)

注意最后一行的含义：发出去的份数里，既有本 rank 自己的原始数据，也有前面轮次已经收集到的数据。这正是 NHR 能在一轮里把信息量翻倍的原因。累计有 Σq_s = N − 1，不多不少刚好收齐。

图 6 · NHR 的轮次（N = 4）。两轮之后持有量从 1 份涨到 4 份。每轮发送的份数 q_s 递增，累计恰好 N−1 = 3 份。

把 NHR 当成一个整体看，它在阶段 1 传递的是 B 片（每份 b 字节），在阶段 2 传递的是整行 A（每份 M·a 字节）。代入上面的 q_s：

NHR 轮次通信距离 Δ发送份数 q阶段 1 的 B 片发送量阶段 2 的 A 片发送量
轮 021bM·a
轮 1122b2·M·a
合计—33b = (N−1)·b3·M·a = (N−1)·M·a

合计一列正好对上第 06 节流量表里 NHR 的两项。这也说明：NHR 的"多跳转发"并没有额外放大有效载荷——每个 rank 发送的总份数就是 N−1，转发的部分早已计入其中。N 不是 2 的幂时，公式同样适用，只是最后一轮的 Δ 会落在非 2 的幂距离上。

08

数据落在哪里、怎么搬过去

四个调用的 buffer 关系，和两条链路的搬运路径。

执行器里这四个调用，逻辑上的输入输出是这样的：

调用链路逻辑输入 → 输出
Intra0 / Inter1Mesh / NHR用户 input → 用户 output
Inter0 / Intra1NHR / Mesh用户 output → 用户 output

阶段 1 从用户输入读，阶段 2 只在用户输出上互相搬。每个源 rank r 的数据直接按最终位置落进 output：

本次循环里，源 rank r 的两片在 output 中的偏移
A 片：r · D + dataOffset0 ,　　dataOffset0 = processedCount × itemSize
B 片：r · D + dataOffset1 ,　　dataOffset1 = dataOffset0 + currCountPart0 × itemSize

也就是说：output 被切成 P 个连续的槽位，每个槽位 D 字节，第 r 个槽位归源 rank r。槽位内部，本次循环要填的 A、B 两片是相邻的；而随着外层循环推进，各个循环的片段会在槽位内依次偏移、跨步出现。等全部循环跑完，每个槽位正好被填满，没有空洞。

图 7 · 两条链路的搬运路径。Mesh 只要一次本地拷贝就被别人读走；NHR 要在 CCL buffer 里经历逐轮收集与转发，代价更高，因此更适合承担"已经收拢成块"的大数据。

为什么阶段 2 也不写回 input
  • 阶段 2 的数据来源是已经落好位的 output，直接在原地收齐即可，不必再绕回输入缓冲区。
  • 这样每个源 rank 的数据只写一次最终位置，避免了"先拼成连续块、再整块复制过去"的额外本地拷贝。
  • 代价是 A、B 两片在 output 里是跨步分布的，所以实现上要用 repeatNum 描述这些不连续的数据片。

"末轮直读"不是无条件生效的

图 7 里 NHR 的"末轮直接从远端 CCL buffer 读进 output"是一个优化，它需要同时满足几个条件：不是 PCIe 链路、没有开启远端内存访问、目标缓冲区确实是用户 output、且 output 与 CCL buffer 不是同一块内存。

这里的"远端内存访问"由执行器按 (OpMode == OFFLOAD) || supportSymmetricMemory 决定——也就是说图模式下或开了对称内存时会走另一条路：直接读写远端 output，此时"末轮直读"这个优化反而被禁用。PCIe 链路则改用 DMA read 的方式收发。

这个优化不改变流量体积，它改变的是方向（写变读）和同步结构——末轮通信可以和"把已到达的片从本地 scratch 拷进 output"并行做。所以它影响的是时间，而不是第 06 节算的字节数。

09

时间模型：数据量不等于耗时

把前面算出来的四个流量，装进一个粗糙但有用的式子。

按当前实现的阶段依赖关系，一次循环的耗时结构可以写成：

一次循环
T ≈ max( TMesh(a),　TNHR(b) )　　← 阶段 1，两项并行
　 + max( TNHR(M·a),　TMesh(N·b) )　← 阶段 2，两项并行
　 + T阶段同步

这里的 T_Mesh(·) 和 T_NHR(·) 是各自模板在给定数据量下的耗时，它们内部包含各自的搬运、轮次同步和资源竞争。所以：

三条使用这个模型的注意事项
  • 数据量本身不能直接等同于耗时。把 V_Mesh 和 V_NHR 相减得到的大小关系，只在两条链路"每字节成本相同"时才等于时间关系。
  • 阶段 1 和阶段 2 的瓶颈可能不是同一条链路。阶段 1 比的是 a 和 b；阶段 2 比的是 M·a 和 N·b。M ≠ N 时，两边的最优 ρ 会互相拉扯。
  • 同步是串行的。两个阶段之间的同步不参与并行，它是纯粹的额外开销。

把第 06 节的流量公式代进"阶段 1 平衡"这个条件：a 和 b 的比等于两条链路的速率比。而"阶段 2 平衡"给出的比则是 M·a : N·b 等于速率比。两者只有在 M = N 时才可能同时满足——这就是为什么切分比例需要跟着拓扑形状走，而不能取一个固定的 0.5。

本节只给出了耗时的结构，没有给出系数。要得到真实的最优 ρ，需要实测两条链路在不同数据量下的带宽与固定开销，那是另一个话题。

10

代码地图与自测

把图上的每个概念，对应到真实源码的位置。

先分清"算法名"和"执行器类"

建议的阅读顺序

「切分比例 → 四组调用 → 阶段同步 → NHR 轮次」：先在执行器里跟一遍 multipleDimensionSplitRatio 如何变成两片的元素个数（注意取整与 4K 对齐的滚存），再看四组模板调用分别绑定了哪些 buffer（阶段 2 的 in/out 都是用户 output），然后确认阶段之间靠什么同步（线程 notify，不是网络 barrier），最后进入 NHR 模板核对每轮的 q_s 与源 rank 序列。

自测

Q1：ρ 变大，两条链路的流量各自怎么变？总发送量呢？

ρ 是 B 片比例。B 片走"先 NHR 后 Mesh"，所以 ρ 变大 → Mesh 流量变大、NHR 流量变小。

总发送量 V_Mesh + V_NHR = (P−1)·d 保持不变，与 ρ 无关。调切分比例只是在两条链路之间搬流量，不会让总量变少。

Q2：M = 2、N = 8 时，流量均衡点 ρ* 大概是多少？为什么不是 0.5？

代入 ρ* = (M·N − 2M + 1) / [2(M−1)(N−1)] = (16 − 4 + 1) / (2 × 1 × 7) = 13/14 ≈ 0.93。

不是 0.5 的原因：两条链路的公式不对称。V_Mesh 的上限是 (M−1)·N·d，V_NHR 的上限是 (N−1)·M·d。只有 M = N 时这两个上限才相等，交点才会落在中点。

Q3：为什么阶段 2 必须等阶段 1 全部完成？

因为阶段 2 传播的数据块，正是阶段 1 收集的产物。A 片要先在本行收齐成 M·a，才能作为一个完整块沿另一维扩散；B 片同理要先收齐成 N·b。

如果不等，阶段 2 传出去的就会是不完整的块，接收方也拼不出正确结果。

Q4：NHR 一共发 N−1 份，为什么"转发"不会让流量翻倍？

因为"份"统计的粒度不是"本 rank 自己的数据"。第 s 轮发出的份数 q_s 里，既包含本 rank 原始数据，也包含前面轮次收到的数据。

累计 Σq_s = N − 1，正好等于"每个 rank 需要贡献给其他 N−1 个 rank 的数据量"。转发是被计入这 N−1 份里的，不是额外的。

Q5：如果两条链路带宽差很多，ρ 应该往哪边偏？

让快的那条链路多背一点。具体做法是让两条链路的时间尽量相等，而不是让字节数相等。

也就是说，第 06 节算出的 ρ* 只是"字节均衡点"，实际要把 ρ 从它出发，朝着"给快链路加负载"的方向再挪一截。
